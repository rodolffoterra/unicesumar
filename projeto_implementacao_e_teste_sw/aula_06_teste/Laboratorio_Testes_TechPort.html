Objetivo do laboratório

Nesta prática vamos executar, pelo terminal, diferentes ferramentas de teste e qualidade utilizadas no ecossistema Python. O objetivo não é apenas “rodar comandos”, mas aprender a interpretar o que cada resultado significa.
TechPort ↓ Código ↓ Testes ↓ Análise ↓ Evidências ↓ Qualidade

1. Preparar o ambiente

1

Entre na pasta do projeto

cd techport
2

Ative a .venv

.\.venv\Scripts\Activate.ps1

Ao ativar corretamente, o terminal deve mostrar algo parecido com:

Assim instalamos, de uma única vez, as bibliotecas da aplicação e as ferramentas de teste.

2. pytest — Testes automatizados

Pergunta principal: o comportamento obtido é igual ao comportamento esperado?

python -m pytest -vv -s
PASSED

O teste executou e o resultado obtido foi igual ao esperado.

FAILED

O teste executou, mas o resultado obtido foi diferente do esperado.

ERROR

O teste não conseguiu ser preparado ou executado corretamente.

SKIPPED

O teste existe, mas foi ignorado naquela execução.

Exemplo de teste simples

import pytest

@pytest.mark.unit
def test_somar():
    # Arrange
    a = 2
    b = 3

    # Act
    resultado = a + b

    # Assert
    assert resultado == 5

Exemplo de regra de negócio com MySQL

Regra usada na aula: todo chamado da semana deveria possuir técnico atribuído. 
SELECT
    COUNT(*) AS quantidade
FROM chamados
WHERE
    YEARWEEK(data_abertura, 1) = YEARWEEK(CURDATE(), 1)
    AND tecnico_id IS NULL;
Esperado = 0 chamados sem técnico Obtido = 9 chamados sem técnico 9 ≠ 0 ↓ FAILED
Exemplo de mensagem: 
AssertionError: Foram encontrados 9 chamado(s) sem técnico.
assert 9 == 0

3. Cobertura de testes — pytest-cov

Pergunta principal: quanto do código foi exercitado pelos testes?

python -m pytest --cov=app --cov-report=term-missing
Coluna Significado
Name Arquivo analisado.
Stmts Quantidade de instruções executáveis.
Miss Quantidade de instruções não executadas pelos testes.
Cover Percentual de cobertura.
Missing Linhas que não foram alcançadas pelos testes.

Exemplo

app\core\config.py      13     0   100%
app\core\security.py    10     2    80%   12, 17
app\api\routes.py       93    93     0%   1-513
TOTAL                 1012   958     5%
Importante: 100% de cobertura não significa 100% de qualidade. Cobertura indica que linhas foram executadas, não que todas as regras estejam corretas.
TESTES 66,7% de sucesso ≠ COBERTURA 5% do código

4. Ruff — Qualidade do código

Pergunta principal: existem problemas de qualidade detectáveis estaticamente?

python -m ruff check .

O Ruff analisa o código sem executar a aplicação.

Exemplo de resultado

app/main.py:10:1: F401 `os` imported but unused
ParteSignificado
app/main.pyArquivo onde o problema foi encontrado.
10Linha.
1Coluna.
F401Código da regra.
imported but unusedDescrição do problema.
Ruff é uma ferramenta de análise estática. Ele ajuda a encontrar problemas cedo, antes de executar ou entregar a aplicação.

5. mypy — Validação de tipos

Pergunta principal: os tipos declarados e utilizados são coerentes?

python -m mypy app

Exemplo

def calcular_idade() -> int:
    return "30"
Declarado int ↓ Retorno real str ↓ Incompatibilidade

Exemplo de mensagem

error: Incompatible return value type
(got "str", expected "int") [return-value]
TermoInterpretação
expectedTipo que o código declarou como esperado.
gotTipo que o mypy encontrou.
return-valueCategoria do problema.
Passar no mypy não significa que a regra de negócio está correta. O mypy verifica tipos, enquanto pytest verifica comportamento.

6. Bandit — Segurança SAST

Pergunta principal: existem padrões potencialmente inseguros no código?

python -m bandit -r app
Código Python ↓ Bandit ↓ SAST ↓ Achados de segurança

Como interpretar um achado

>> Issue: [B602:subprocess_popen_with_shell_equals_true]
Severity: HIGH
Confidence: HIGH
CWE: CWE-78
Location: app/utils/exemplo.py:20:4
CampoSignificado
B602Regra de segurança acionada.
SeverityImpacto potencial.
ConfidenceConfiança da ferramenta no achado.
CWECategoria padronizada de fraqueza.
LocationArquivo e linha para investigação.
Um achado do Bandit não é automaticamente uma vulnerabilidade confirmada. Ele indica um padrão que deve ser analisado no contexto do código.

7. pip-audit — Segurança das dependências

Pergunta principal: alguma biblioteca instalada possui vulnerabilidade conhecida?

python -m pip_audit
Dependências ↓ Versões instaladas ↓ pip-audit ↓ Base de vulnerabilidades ↓ SCA

Exemplo real obtido no laboratório

Found 43 known vulnerabilities in 13 packages
Isso significa 43 vulnerabilidades conhecidas distribuídas em 13 pacotes. Não significa 43 bibliotecas e não significa que o TechPort foi invadido.

Exemplo de linha

requests  2.32.5  PYSEC-2026-2275  2.33.0
CampoSignificado
requestsPacote afetado.
2.32.5Versão instalada.
PYSEC-2026-2275Identificador da vulnerabilidade conhecida.
2.33.0Versão indicada com correção.

Cuidados com atualização

Nem toda dependência deve ser atualizada isoladamente. Exemplo: FastAPI depende de Starlette. Atualizar Starlette para uma versão incompatível pode quebrar a aplicação.
Identificar pacote ↓ Ver versão instalada ↓ Ver vulnerabilidade ↓ Ver Fix Version ↓ Verificar compatibilidade ↓ Atualizar ↓ Executar pytest ↓ Executar pip-audit novamente
